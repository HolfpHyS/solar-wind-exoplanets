# Сводный аудит решений в `pro`

Дата аудита: 2026-07-29.

## 1. Краткий вывод

Основной сохранённый пайплайн `dl_pro` математически согласован с кодом и
чекпоинтами. После распаковки текущего датасета и запуска в подходящем Python-
окружении он точно воспроизводит сохранённые метрики:

| Метрика на фиксированном validation, 123 объекта | Значение |
|---|---:|
| `XUVInt`, oracle best-of-5 MAPE | 10.7811% |
| `Helium`, oracle best-of-5 MAPE | 9.6579% |
| `logMsw`, oracle best-of-5 MAPE | 0.6302% |
| `H2a`, ROC-AUC | 0.994712 |
| `H2a`, accuracy при пороге 0.5 | 0.967480 |

Но интерпретировать эти числа как качество готового одноответного решения
нельзя. Для каждой строки и каждого регрессионного параметра метрика смотрит на
истину и выбирает лучший из пяти кандидатов. Текущий scorer в
[`participant/score.py`](../participant/score.py) принимает только один ответ.
Для реализованного в ноутбуке single-answer варианта — среднего всех 25 голов —
получаются `31.93 / 25.11 / 1.56%`, ROC-AUC `0.9947` и приблизительно
`20.28` итоговых единиц по текущей формуле scorer.

После основного аудита выполнен отдельный OOF-ranker pilot: кандидаты для всех
490 training-объектов получены только от generator-моделей, которые этот
объект не видели. Objective выбран по producer-fold CV, после чего ranker
переобучен на всех OOF-кандидатах. На очищенном от exact train/dev overlap
historical development subset из 118 объектов frozen `combined` ranker снизил
deployable XUV top-1 MAPE с `23.71%` до `19.12%` на одном и том же пуле из
10 кандидатов. Физическая joint-метрика при этом не улучшилась. Полный протокол
приведён в [`OOF_RANKER_REPORT.md`](OOF_RANKER_REPORT.md).

Сводный вердикт:

| Область | Оценка |
|---|---|
| Сохранённый инференс `dl_pro` | Воспроизводится после ручной настройки пути и окружения |
| Переобучение `dl_pro` | Частично воспроизводимо; конфигурация видна, но окружение и детерминизм не зафиксированы |
| Прямая утечка validation в основном `dl_pro` | Не обнаружена |
| Утечка в `aux_conditioning`, `xuv_max`, `aux_pretrain` | Source исправлен; основной conditioned run полностью переобучен |
| OOF single-answer ranker | XUV top-1 улучшен `23.71% → 19.12%`; joint safety не улучшена |
| Честность финальной оценки | Недостаточная: один validation многократно использован для early stopping, выбора архитектур и эвристик |
| Применимость headline best-of-5 к текущему submission | Не применимо без изменения формата соревнования |
| Доказательство обобщения на новые планеты/реальные наблюдения | Отсутствует |
| Утверждение «лучше публикации по идентичному протоколу» | Подтверждено не полностью; есть различия датасета, holdout и протокола `Msw` |

Итого: `dl_pro` — полезная и технически рабочая исследовательская модель
покрытия множества возможных решений. Это пока не валидированная production-
модель и не готовое одноответное конкурсное решение.

## 3. Данные и разбиение

### 3.1. Состав

Текущий ZIP и `participant/new_dataset_V3` совпадают по содержимому датасета;
в распакованной копии дополнительно лежит `.DS_Store`.

- 613 каталогов-прогонов;
- в каждом есть `Absorption.dat` и `parameters.txt`;
- 305 объектов с `H2a=0`, 308 с `H2a=1`;
- диапазоны целей:
  - `XUVInt`: 1–60;
  - `Helium`: 0.001022–0.300022;
  - `Msw`: `1e11–9.9e13`;
  - `H2a`: 0/1.

Все 613 текущих файлов конечны, скоростная координата строго возрастает. После
удаления карантинного прогона ни один объект не отбрасывается условием
`velocity_span < 5`.

35 профилей имеют неполную исходную сетку: 91, 81 либо 41 точку, с отсутствующим
правым или обоими краями. Код интерполирует всё на 101 точку `[-5, 5]` с шагом
0.1 и заполняет неизвестные края нулями. Такое заполнение создаёт искусственный
маркер происхождения/типа сетки. Поскольку затем нули превращаются в константу
`log10(1e-7)`, сеть может использовать этот артефакт. Это не target leakage, но
это риск shortcut learning.

### 3.2. Split

В основном решении используется один split:

```text
train_test_split(
    indices,
    test_size=0.2,
    random_state=42,
    stratify=H2a,
)
```

Получается:

| Часть | Всего | `H2a=0` | `H2a=1` |
|---|---:|---:|---:|
| train | 490 | 244 | 246 |
| validation | 123 | 61 | 62 |

`checkpoints/preproc.npz` содержит именно эти индексы. Сохранённые
`y_mean`, `y_std`, `x_scale` точно совпали с повторным расчётом на текущем ZIP,
поэтому основной checkpoint был обучен на этой версии 613-объектного набора.
`participant/true.csv` также точно соответствует этим 123 объектам и их порядку.

Недостатки split:

- стратификация есть только по `H2a`, но не по планете, физической конфигурации
  или семейству симуляций;
- четыре validation-объекта имеют в train полное совпадение всех четырёх
  target-полей;
- один validation-профиль после интерполяции побитово совпадает с train-
  профилем, но имеет другой `Helium`:
  `XUV5Msw2p5e12He0p04` против `XUV5Msw2p5e12He0p05`;
- 61% validation-профилей имеют очень близкого train-соседа с
  стандартизованным pointwise RMSE не более 0.1; абсолютный порог зависит от
  выбранной нормировки, но общая картина показывает плотное локальное
  пересечение.

Удаление четырёх validation-объектов с повторяющимися targets меняет headline
best-of-5 лишь с `10.78 / 9.66 / 0.63` на `11.07 / 9.83 / 0.61%`. То есть
несколько точных дублей не объясняют весь результат, но random row split всё
равно измеряет главным образом интерполяцию внутри одной сетки симуляций, а не
перенос на новую планету или новый физический режим.

Имена каталогов местами не согласованы с `parameters.txt`; модель правильно
использует значения из файла параметров, но ID может вводить в заблуждение.
Например, каталоги с разными XUV/Msw в имени встречаются в группах с одинаковыми
фактическими targets.

## 4. Основная архитектура `dl_pro`

Источники:

- [`model_defs.py`](model_defs.py);
- [`train_and_save.py`](train_and_save.py);
- [`infer.py`](infer.py);
- `dl_pro.ipynb`;
- [`training_plots/architecture.png`](training_plots/architecture.png).

### 4.1. Вход и препроцессинг

Профиль превращается в tensor `(2, 101)`:

1. линейный канал `profile / x_scale`;
2. `log10(clip(profile, 1e-7))`, стандартизованный отдельно внутри каждого
   профиля.

Регрессионные targets:

```text
log10(XUVInt), log10(Helium), log10(Msw)
```

Они z-нормируются статистиками только train:

```text
x_scale = 0.5039860010
y_mean  = [ 1.28690972, -1.29155032, 12.92801106]
y_std   = [ 0.38693556,  0.43044262,  0.71736766]
```

Для ранкера строится PCA-16 лог-профилей. Центр, SVD-базис и нормировка PCA
считаются только по train. В сохранённом ноутбуке 16 компонент объясняют
99.995% train-дисперсии.

### 4.2. CNN

```text
(B, 2, 101)
→ Conv1d 2→64, k=5, pad=2 → BatchNorm → ReLU → MaxPool2
→ Conv1d 64→128, k=5, pad=2 → BatchNorm → ReLU → MaxPool2
→ Conv1d 128→128, k=5, pad=2 → BatchNorm → ReLU → MaxPool2
→ (B, 128, 12)
→ Flatten
→ (B, 1536)
```

От общего embedding отходят:

- пять регрессионных голов `1536 → 256 → 3`, ReLU, dropout 0.2;
- одна классификационная голова `1536 → 128 → 1`, ReLU, dropout 0.2.

Размерности выхода:

```text
регрессия: (B, 5, 3)
H2a logit: (B,)
```

Число параметров:

| Компонент | Параметры |
|---|---:|
| Encoder | 124,480 |
| Одна regression head | 394,243 |
| Пять regression heads | 1,971,215 |
| `H2a` head | 196,865 |
| Одна CNN целиком | 2,292,560 |
| Пять CNN | 11,462,800 |
| Ранкер | 71,169 |
| Весь сохранённый ансамбль | 11,533,969 |

### 4.3. Loss

Для каждого объекта вычисляется MSE совместного трёхмерного вектора для каждой
из пяти голов:

```text
per_head = mean_over_3_targets((prediction - truth)²)
WTA = mean_over_batch(min_over_heads(per_head))
      + 0.1 * mean_over_batch_and_heads(per_head)
total = WTA + BCEWithLogits(H2a)
```

Первый член специализирует ближайшую к истине голову. Второй не даёт остальным
головам полностью перестать обучаться. Это WTA-покрытие, но явного diversity-
штрафа между головами в данной реализации нет.

### 4.4. Обучение CNN

| Параметр | Значение |
|---|---|
| Количество моделей | 5 |
| Seeds | 0, 1, 2, 3, 4 |
| Эпохи | 400 на модель |
| Batch size train / val | 64 / 256 |
| Optimizer | Adam |
| Learning rate | `1e-3` |
| Weight decay | 0 |
| Scheduler | CosineAnnealingLR, `T_max=400`, `eta_min=0` |
| Аугментация | Gaussian noise, `σ=0.005 * profile.max()` |
| После шума | clip снизу до `1e-7` |
| Checkpoint | минимум `WTA + BCE` на validation за 400 эпох |
| Early stopping | нет; только выбор лучшей эпохи постфактум |

Лучшие эпохи из `histories.npz`:

| Seed | Лучшая эпоха | Best val loss | Финальный val loss |
|---:|---:|---:|---:|
| 0 | 90 | 0.328345 | 0.537688 |
| 1 | 177 | 0.191443 | 0.202510 |
| 2 | 271 | 0.154599 | 0.172000 |
| 3 | 218 | 0.214498 | 0.240022 |
| 4 | 298 | 0.172543 | 0.185260 |

Seed 0 заметно переобучается после 90-й эпохи. Выбор лучшего checkpoint это
компенсирует, но одновременно делает validation частью model selection.

`make_training_plots.py` выполняет отдельное повторное обучение, а не читает
историю из checkpoint-файлов. Тем не менее текущие checkpoints дали те же
минимальные loss, что и NPZ, с точностью около `1e-7`, то есть два запуска были
практически идентичны.

### 4.5. Ранкер

Вход ранкера:

```text
16 PCA-признаков профиля + 3 нормированных log-target кандидата = 19
```

Архитектура:

```text
19 → 256 → ReLU → Dropout(0.2)
   → 256 → ReLU → Dropout(0.2)
   → 1 logit
```

Формируется 4,373 train-пары:

- истинная пара `(profile, own targets)`;
- две положительные perturbations с `σ=0.05` в нормированной target-шкале;
- до трёх случайных negatives с distance targets > 0.5;
- до трёх hard negatives: близкий PCA-профиль, но distance targets > 0.8.

Ранкер обучается 3,000 шагов по случайным batch 256, Adam `1e-3`,
`weight_decay=1e-5`, BCE. Validation, scheduler и checkpoint selection для него
нет. Ранкер видит истинные и искусственно возмущённые targets, но не обучается
на распределении ошибок реальных CNN-кандидатов.

### 4.6. Отбор кандидатов

Пять CNN дают 25 совместных кандидатов. Первый выбранный кандидат имеет
максимальный score ранкера. Следующие четыре максимизируют:

```text
минимальное расстояние до уже выбранных + 0.02 * score
```

Критические детали:

- после первого элемента рассматриваются все 25 кандидатов, а не правдоподобный
  top-M;
- на validation 47 из 615 выбранных позиций имели худший score-rank 24;
- logits выбранных кандидатов доходили до `-101.18`;
- поэтому строка CLI «топ-5 кандидатов (по убыванию ранга)» неверна: по rank
  выбран только №1, остальные упорядочены diversity-эвристикой;
- выбранные predictions не ограничены train-domain. На validation встречались
  XUV `0.27–99.4`, He `0.0013–7.7`, Msw `3.1e9–1.66e14`.

Это объясняет, почему метод хорошо покрывает возможные ветви в oracle-метрике,
но часть пятёрки ранкер сам считает физически крайне неправдоподобной.

### 5.1. Альтернативные архитектуры

**TCN**

- четыре residual-блока;
- каналы `(64, 64, 128, 128)`;
- две causal weight-normalized Conv1d в блоке;
- kernel 5, dilations 1/2/4/8, dropout 0.2;
- receptive field 121 > длины 101;
- embedding — последний timestep;
- encoder 358,848 параметров, полная multi-head модель 544,464.

Каузальность здесь не соответствует естественной симметрии спектрального
профиля и не дала преимущества.

**InceptionTime**

- шесть Inception-модулей;
- kernels `(9, 19, 39)`;
- bottleneck 32;
- четвёртая max-pool ветка;
- 128 каналов после конкатенации;
- residual каждые три блока;
- global average pooling;
- encoder 407,040 параметров, полная модель 592,656.

**Physical conditioning**

- базовый CNN encoder;
- вспомогательная planet head `1536 → 64 → 3`;
- softmax по трём известным планетам умножается на фиксированную таблицу
  `(3, 9)` физических параметров;
- полученный девятимерный вектор добавляется к embedding;
- loss содержит `0.3 * CrossEntropy(planet)`;
- модель 2,402,643 параметра.

`PHYS_t` — глобальный tensor, не зарегистрированный через `register_buffer`, и
не входит в `state_dict`. Веса такой модели нельзя корректно перенести без
отдельного восстановления таблицы. Кроме того, сеть умеет выдавать только смесь
трёх известных векторов; текущая реализация не подтверждает заявленный перенос
на произвольную новую планету.

**XUV-max**

- та же conditioned-архитектура;
- 8 WTA-голов;
- 7 seeds, итого 56 кандидатов;
- около 3.59 млн параметров на модель;
- ранкер оставляет top-M, затем кандидаты разносятся только по оси XUV.

Параметр `M` перебирался и выбирался на том же validation. Это дополнительная
оптимизация под oracle-метрику.

**p-winds pretrain**

- 6,000 синтетических профилей;
- 8 планет из внешнего каталога;
- synthetic split 90/10;
- pretrain encoder: 60 эпох, batch 128, Adam `1e-3`, cosine;
- fine-tune: три seeds × 400 эпох с тем же conditioned WTA-loss;
- `VV * 10` без проверки считается скоростью в км/с.

Претрейн не улучшил контрольный no-pretrain эксперимент. Его красивые
oracle-of-15 числа объясняются большим `k` и не должны сравниваться с
best-of-5.

| Decision Tree | depth 3, ручные признаки | — | 64.8% |

Важности `fwhm`, `width10`, `mean_v` получены не из пяти PCA-квантильных
моделей, которые дают результат 11.8%, а из отдельной median-модели на ручных
признаках. Поэтому этот график даёт общую физическую интерпретацию, но не
объясняет непосредственно predictions лучшего XGBoost-ансамбля.

PySR в сохранённом запуске отсутствовал, поэтому заявленная символьная
регрессия фактически не проводилась.

### 5.3. Методологический эксперимент best-of-k

`methodology_note_bestofk.ipynb` правильно демонстрирует слабость метрики:

- пять фиксированных train-квантилей XUV без использования профиля дают 19.1%;
- пять равномерных точек дают 28.1%;
- 10 равномерных точек дают 12.2%;
- 20 равномерных точек дают 5.0%.

Это важная и корректная оговорка: best-of-k механически улучшается при росте
`k`. Сравнивать можно только одинаковый `k`, а применять метрику имеет смысл,
если все кандидаты действительно будут проверяться независимой forward-моделью
или наблюдением.

## 6. Аудит утечки данных

### 6.1. Основной `dl_pro`: прямой preprocessing leakage не найден

В `train_and_save.py`:

- split создаётся до расчёта нормировок;
- `x_scale`, `y_mean`, `y_std` считаются только на `idx_train`;
- PCA basis и PCA-нормировка считаются только на train;
- пары ранкера используют только train;
- validation augmentation отключена.

Validation targets не входят в train-признаки и не используются при обучении
ранкера. Это хорошая часть реализации.

### 6.2. Реальная transductive leakage в conditioned-ветках

В `aux_conditioning`, `xuv_max` и fine-tune части `aux_pretrain` классификатор
планеты обучается так:

```python
clf.fit(Z[known], pnames[known])
```

Ограничения на `idx_train` нет. В fit попадают:

```text
466 известных train-объектов
116 известных validation-объектов
```

Затем этот классификатор создаёт псевдометки для 31 объекта с неизвестным
`PName`, из которых 24 лежат в train.

Контрольный пересчёт показал: если fit делать только по known-train, меняются
11 из 31 псевдометок, включая 8 из 24 train-псевдометок. Следовательно,
validation-данные материально влияют на train supervision. Результаты
`aux_conditioning`, `xuv_max` и обеих веток `aux_pretrain` нельзя считать
чистым holdout.

Исправление: строить planet classifier внутри train, а для train-псевдометок
использовать out-of-fold predictions. Validation следует только transform-ить.

### 6.3. Validation reuse / model-selection leakage

Даже в чистом `dl_pro` одни и те же 123 объекта используются:

- 400 раз на модель для выбора лучшей эпохи;
- для сравнения пяти seeds;
- для сравнения CNN, TCN, InceptionTime и conditioning;
- для выбора количества голов и моделей;
- для выбора `0.02` в diversity score;
- для перебора top-M в XUV-max;
- для выбора финальной стратегии;
- для итоговых таблиц и bootstrap CI.

Early stopping сам по себе нормален, если после него есть независимый test.
Здесь такого test нет. Поэтому validation превратился в development set, а его
метрики оптимистичны как финальная оценка.

Bootstrap в `paper_comparison` учитывает только разброс объектов условно на уже
выбранных моделях. Он не учитывает variability по split, seed, архитектуре и
гиперпараметрам и не исправляет selection bias.

### 6.4. Утечки/риски в других файлах

- В `eda` PCA строится на всей выборке до 5-fold CV. Это мягкая
  unsupervised preprocessing leakage в EDA-оценках.
- `aux_data/xuv_candidates.npz` прямо содержит `y_true (123, 3)` и
  `y_train (490, 3)`. Для приватного исследовательского кэша это допустимо, но
  такой файл нельзя включать в пакет слепого тестирования.
- Downstream-ноутбуки не используют `y_true` как per-row вход селектора, но
  используют его для выбора стратегии и гиперпараметра `M` на том же holdout.
- Random row split содержит точные и близкие cross-split варианты; это
  структурное пересечение train/validation, хотя не прямое копирование labels
  в модель.

## 7. Корректность метрик и заявлений

### 7.1. Best-of-5 — oracle coverage, а не обычная точность

Для каждого объекта код вычисляет пять кандидатов, смотрит истинный target и
берёт минимальную ошибку. Более того, лучший индекс выбирается отдельно для
XUV, He и Msw.

Только для 22.8% validation-профилей один и тот же кандидат оказывается лучшим
сразу по всем трём координатам. Поэтому строка `10.8 / 9.7 / 0.6` обычно не
описывает ни один совместный физический вектор.

Если oracle заставить выбрать одну и ту же строку пятёрки по совместной ошибке,
получается примерно:

```text
XUV 15.62%, He 11.92%, logMsw 1.21%
```

Это всё ещё oracle, потому что выбор строки использует истину.

### 7.2. Текущий scorer принимает один ответ

Текущий формат:

```text
id,XUVInt,Helium,logMsw,H2a
```

Не существует способа на blind test выбрать «лучшую из пяти» без доступа к
истине. Для сравнения:

| Point estimator | XUV | He | logMsw | Текущий итоговый score |
|---|---:|---:|---:|---:|
| Среднее 25 голов в log-шкале | 31.93% | 25.11% | 1.56% | 20.28 |
| Top-1 ранкера | 21.37% | 59.96% | 1.46% | 28.76 |

Top-1 ранкера особенно плох по He, поэтому ранкер не решает задачу выбора
единственного ответа. Нужен OOF-обученный агрегатор либо другой калибратор.

### 7.3. Масштаб `logMsw`

`0.63%` — MAPE чисел `log10(Msw) ≈ 11–14`, а не MAPE физического `Msw`.
Для тех же oracle-предсказаний:

- mean absolute error около 0.080 dex;
- MAPE физического `Msw` около 19.9%.

Метрика `logMsw` соответствует текущему scorer, но в тексте её нельзя
интерпретировать как «ошибка массовой потери 0.6%».

`infer.py` печатает `10**logMsw`, то есть физический `Msw`. Это значение нельзя
без преобразования копировать в submission, где требуется `logMsw`.

### 7.4. Сравнение с «публикацией»

Локальный источник `absorption_nn (3).pdf` — незавершённый draft:

- авторы указаны как `A. Author`, `B. Author`;
- email — `author@example.org`;
- в разделе обучения остались незаполненные гиперпараметры;
- в формуле есть редакторская заглушка.

Поэтому называть его значения независимо опубликованным benchmark без внешней
ссылки нельзя.

Даже относительно этого draft сравнение не полностью одинаковое:

1. PDF использует 614 объектов и split 491/123; `pro` использует очищенные
   613 и split 490/123.
2. Validation-наборы этих двух разбиений пересекаются по 115 из 123 объектов;
   восемь объектов различаются.
3. В PDF пять голов есть только у XUV и He. `logMsw` предсказывает single head.
   В `pro` для `logMsw` применяется oracle best-of-5, поэтому `0.6%` против
   `1.8%` — не сравнение одного протокола. Сопоставимее single `1.56%`.
4. PDF использует отдельные модели по targets и другой transformer/cosine
   ranker; `pro` предсказывает совместные тройки и использует PCA+MLP.
5. Аугментации и optimizer также различаются.

Для XUV и He best-of-5 MAPE концептуально сопоставим, но это не тот же holdout и
не независимый test.

Есть и конкретная арифметическая ошибка в тексте `overview_figures`: он
утверждает, что CI Helium для модели A и draft не пересекаются, приводя
`15.8 < 15.4`. На самом деле 15.8 больше 15.4, интервалы
`[9.7, 15.8]` и `[15.4, 20.6]` пересекаются. Для модели B интервалы действительно
не пересекаются, но вывод всё равно условен на многократный model selection.

### 7.5. Несогласованность XUV-артефактов

`aux_data/xuv_candidates.npz` не создаётся ни одной имеющейся ячейкой или
скриптом. Его происхождение не воспроизводится.

Сохранённые цифры конфликтуют:

- прямой `xuv_max.ipynb`: XUV 7.7%, oracle-of-56 3.2%;
- cache-based `xuv_single_pentad`: XUV 6.0%, oracle-of-56 2.4%;
- `overview_figures` смешивает XUV 7.7% прямого запуска и He 12.4% другого
  cache-run в одной строке.

Это не один эксперимент, а как минимум два набора кандидатов. Их нужно
разделить по run ID и генерировать кэш кодом.

## 8. Воспроизводимость

### 8.1. Что воспроизводится

После распаковки ZIP рядом с `pro` и использования окружения с PyTorch:

- все checkpoints загружаются;
- одиночный инференс работает;
- validation-таблица `infer.py` воспроизводится точно;
- split и нормировки совпадают с текущим архивом;
- loss checkpoints совпадает с histories;
- cache-based лёгкие notebooks повторяют сохранённые числа.

### 8.2. Что не работает «из коробки»

1. Команда из docstring `python3 infer.py` использует системный/Homebrew Python,
   где в текущем окружении нет даже NumPy/PyTorch/sklearn.
2. `python pro/infer.py` без аргумента падает с `FileNotFoundError`: скрипт
   ожидает корневой `new_dataset_V3`, но данные находятся в ZIP и в
   `participant/new_dataset_V3`.
3. `pro/new_dataset_V3` — сломанная ссылка на отсутствующую корневую папку.
4. `train_and_save.py` ломается по тому же пути.
5. Старый `archive/participant_original/baseline.py` ищет данные в
   `pro/archive/new_dataset_V3`, которой нет.
6. Notebooks полагаются на текущий working directory и относительные пути.
7. В проекте нет `requirements.txt`, `environment.yml`, lock-файла, Dockerfile
   или инструкции верхнего уровня для `pro`.

### 8.3. Что мешает полному retrain

- версии библиотек не зафиксированы;
- `torch.use_deterministic_algorithms`, cuDNN/MPS deterministic settings и
  сведения о hardware не фиксируются;
- альтернативные модели не сохраняют checkpoints;
- `preproc.npz` хранит только числовые индексы, а не имена объектов и хэш
  датасета;
- изменение сортировки/состава каталогов молча меняет значение индексов;
- кэш XUV не имеет генератора и metadata run;
- `planet_params.csv` не содержит даты выгрузки, URL/идентификаторов источника;
- `aux_pretrain` импортирует `p_winds` и Astropy до проверки наличия кэша, так
  что даже использование готового NPZ требует этих пакетов;
- notebook outputs `eda` устарели: сохранено 614 объектов, текущий rerun видит
  613; несколько CV-чисел меняются;
- `overview_figures` содержит вручную переписанные метрики и CI.

Seeds NumPy/PyTorch улучшают повторяемость, и на текущей машине два основных
запуска действительно совпали. Но перенос CPU ↔ MPS ↔ CUDA или изменение
версии PyTorch не обязан дать те же веса.

## 10. Финальная оценка

Сильная сторона папки `pro` — ясная идея многозначного обратного отображения,
совместные трёхмерные WTA-кандидаты, аккуратный train-only preprocessing в
основном пайплайне и реальные сохранённые веса, которые подтверждают
заявленные числа.

Главная слабость — смешение трёх разных задач:

1. покрыть истину множеством кандидатов;
2. выбрать один физически правдоподобный кандидат без знания истины;
3. получить честную оценку обобщения.

Первая задача решена убедительно на текущем development split. Вторая пока
решена слабо: mean-25 и top-1 существенно хуже oracle. Третья не доказана из-за
повторного использования одного holdout и структурного пересечения данных.
Transductive leakage присутствует в исторических conditioned outputs; source
исправлен, а основной эксперимент переобучен по clean-протоколу (раздел 11).

Поэтому основной `dl_pro` стоит сохранить как исследовательский baseline
многокандидатного retrieval. Для финального соревнования или научного вывода
нужны независимый протокол, single-answer адаптер либо официальный multi-answer
scorer и полностью воспроизводимый run manifest.

## 11. Post-fix: устранение leakage и пересчёт `aux_conditioning`

29 июля 2026 года одинаковый leaky-fit классификатора планеты исправлен в
`aux_conditioning.ipynb`, `xuv_max.ipynb` и `aux_pretrain.ipynb`: fit теперь
выполняется только на `known ∩ train`. В основном conditioned-эксперименте
классификатор использовал 466 training-строк и 0 validation-строк. Исправление
изменило 11/31 псевдометок относительно старого протокола, в том числе 8/24
псевдометок training split.

`aux_conditioning` полностью переобучен: пять seeds × 400 эпох и ранжировщик
3000 steps. На прежнем development holdout из 123 объектов получены:

| Метрика | Clean train-only run |
|---|---:|
| XUV MAPE, diverse coordinate-wise best-of-5 | **9.0165%** |
| He MAPE, diverse coordinate-wise best-of-5 | **8.6242%** |
| logMsw MAPE, diverse coordinate-wise best-of-5 | **0.6594%** |
| logMsw MAE | **0.08254 dex** |

Для применимого single-answer `ranker top-1` ошибки существенно выше:

Сравнение со старыми `9.8 / 8.9 / 0.5%, AUC 0.998` является ориентировочным:

## 12. OOF-ranker pilot: single-answer после исправления leakage

Следующий пункт плана — обучение selector на реальных OOF-кандидатах — выполнен.
Для 490 outer-train объектов построены кандидаты по пяти
`StratifiedGroupKFold` producer folds. Fold-specific normalization, PCA,
profile scale и planet pseudolabel classifier fit-ились только на producer
train; пересечение pseudolabel fit и prediction rows во всех моделях равно
нулю. Generator и final refit обучались фиксированные 200 эпох без выбора
checkpoint по OOF/dev labels.

Ranker objective выбран по полному producer-fold CV:

| Objective | Pooled OOF-CV XUV top-1 MAPE |
|---|---:|
| XUV | 28.674% |
| Joint | 36.862% |
| **Combined** | **28.107%** |

На primary historical development subset из 118 объектов, после исключения
пяти строк из exact duplicate groups, пересекающих outer train:

| Метрика | Legacy ranker | OOF combined |
|---|---:|---:|
| XUV top-1 MAPE | 23.7096% | **19.1166%** |

Парный percentile bootstrap для top-1 XUV даёт разность
